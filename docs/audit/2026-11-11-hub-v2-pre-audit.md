Status, 2026-11-11: the fix round after this review produced `contracts-near/out/hub.wasm` with sha256 `ef9e1fcee61b4dbd89f9a2051c673c39a2eec480376128a93f23b107f552ea09`, NEAR code hash `H8NHZwWQPwgdYCku8kUR7AqcnbvY28BQGaRU5LhuARFN`, 345,682 bytes.

The reviewed build was hub v2 with sha256 `cf978c32ec76c2967c05384e1533b298c9cbe623274e9542bc07987d9babcd3f`.

Scope: `contracts-near/src` (every file), `contracts-near/src/tests`, `contracts-near/tests` (read, not run), `Cargo.toml`, `build.sh`, `packages/chain/scripts/deploy-hub.ts` (deploy and lock steps), README and `docs/SECURITY.md`.

## Items checked and found correct

- Authorization: every `pub fn` in the `#[near]` impls maps to exactly one guard, and the guard runs before any write. `settle_own` calls `load_budget` first, which only reads. `new`, `on_payout` and `on_reclaim` use `require_self`; the callbacks are not `#[payable]`, so a deposit is refused by near-sdk. `require_self` checks the result count before `is_promise_success`, so a direct call cannot panic it. The `ONE_YOCTO_REQUIRED` methods (`fund_from_credit`, `register_receipt_key`, `withdraw_storage`, `accept_admin`) cannot be reached by a function-call key; `revoke_budget`, `reclaim`, `prune`, `settle_batch`, `settle_own` (zero deposit) and `payout` can, and none of them sends value anywhere but to the owner, the creditor or the caller's own refund.
- `ft_on_transfer`: only the configured token, returns the full amount on every refusal, a deposit is accepted only from the Budget's owner while open, and a panic on the payment path is a NEP-141 refund. No state is written on refusal paths.
- Callbacks: amounts move to `in_flight` (entry and global) before the promise; failures restore with saturating math; an entry with anything in flight is never removed, so the `None` branch of `on_payout` is unreachable; overlapping payouts and reclaims are safe; static gas is a floor (default weight 1).
- Conservation: `total_escrow + total_credits + in_flight` matches the token ledger on every path the unit harness checks, including my PoCs (`assert_solvent`). Netting debits equal credits; debits always belong to an owner in the batch; `ONE_BUDGET_PER_OWNER` holds.
- Storage: every growing write is measured with `storage_usage` (or `borsh_len` for the root record) and charged; Budget, credit and balance records rewritten in place are fixed width; `revoke` growth is prepaid; the root record shrinks on `accept_admin`. Apart from P1's misattribution, every reserve draw is returned to the same Budget on release, so a listed Budget's reserve covers all its payees, and `prune` cannot refund more than was charged. The hub's NEAR never pays: freed bytes with no funder increase the hub's free balance, they never decrease it. Refunds are created after the last check.
- Prune: only after the deadline, which cannot move after expiry (revoke refused after `valid_until`), and both settlement paths check `now <= deadline`, so removing `settled` entries cannot enable a replay. The Budget record stays, so the id cannot be reopened.
- Signatures: voucher and checkout preimages carry distinct tags above 2^31, a versioned domain, hub and network; the Budget id binds hub, network and owner; the acceptance text binds the Budget id, payee, amounts, request hash, timestamp and voucher signature, and its first 4 bytes ("paym", 0x6d796170 < 2^31) cannot parse as a NEAR transaction or a NEP-366 delegate action. Receipt keys are looked up under the Budget's own settler. Small-order and non-canonical keys are refused for agent, receipt and checkout keys (the list matches `EIGHT_TORSION`). Merkle leaves and nodes are domain-separated (0x00/0x01), depth is capped at 32, and batches are keyed by `(settler, batch_id)`.
- Time: all on-chain times are milliseconds from `block_timestamp_ms`; the acceptance's seconds are converted with `checked_mul`; `settle_deadline` cannot overflow because `valid_until <= u64::MAX - 3 days`; `reclaim` and `prune` open strictly after the last settling millisecond.
- Two-step admin: only the named account with exactly one yoctoNEAR can accept; the hub can be neither admin nor pending admin; `propose_admin(None)` withdraws.
- Gas: `settle_batch` is bounded at 100 claims and each claim does one Budget load, one binary search and one signature check; `payout` is bounded at 10 accounts with a gas floor; `prune` at 100 payees.
- Panics leave no partial state: every panic reverts the receipt, and no event is emitted before a possible panic on any path.
- Internal audit fixes F3 to F8: present and covered by regression tests; F4's settlement half is fixed (the settler pays only its batch record), its checkout half is not (P5); hardening item 10 is done through `prune`, and its new reserve logic introduced P1.
- Build: release profile is `codegen-units = 1`, `opt-level = "z"`, `lto = true`, `panic = "abort"`, `overflow-checks = true`; `Cargo.lock` contains no `wee_alloc`. I rebuilt with `sh build.sh` from a clean copy in another directory and got sha256 `cf978c32ec76c2967c05384e1533b298c9cbe623274e9542bc07987d9babcd3f`, equal to `out/hub.wasm` and the README, with no `/Users/` string in the wasm. `cargo clippy --all-targets -- -D warnings` is clean.
- The contract creates no `AddKey`, `DeployContract` or `DeleteAccount` actions; its only promises are NEAR refunds, `ft_transfer` to the token and its two self callbacks, so with no access keys the code cannot change.
